## 6月7日 — 移动端适配 + v3.1.0 + v3.2.0

### 移动端全屏适配

针对 Redmi K60 做的专项适配。

**问题**
- 100vh 在 Android WebView 中不稳定，可能包含状态栏/导航栏区域
- 弹性滚动、下拉刷新干扰体验
- 滚动穿透到父元素

**解决**
- `100vh` → `100%` + `position: fixed; inset: 0`
- `overscroll-behavior: none` 防弹性滚动
- `overscroll-behavior: contain` 防滚动穿透
- WebView 禁用缩放，HTML 完全控制布局
- 全屏沉浸模式，内容延伸到状态栏和导航栏后面

**Android 端**
- `setLoadWithOverviewMode(true)` — 概览模式加载
- `setUseWideViewPort(true)` — 宽视口
- 禁用缩放控件

### 吐槽

Android WebView 的 100vh 是个经典坑。浏览器里 100vh 就是视口高度，但 WebView 里可能把状态栏、导航栏的高度也算进去。解决方案就是不用 vh，用 % + fixed。这种平台差异性，文档里不会告诉你，只有踩过才知道。

v3.1.0 的改动量比 v3.0.0 大得多。版本号、导出、表情包、日记编辑、人设、地图……一天之内塞了这么多功能进去。最坑的是移动端导出。PC 端直接创建 `<a>` 标签点击下载就行，移动端不行。得用 Web Share API，而且还要处理 fallback。每个平台的"下载文件"这件小事，实现起来都不一样。

还有地图。Leaflet 本身挺好用的，但在 WebView 里嵌地图，触摸事件冲突是家常便饭。拖地图和拖页面打架，得手动处理 `touch-action`。

仓库清理是那种"不紧急但重要"的事。空仓库放在那里不碍事，但看着心烦。删了干净。

6 号到 7 号，从 v3.0.0 到 v3.2.0，两天三个版本。功能从"能跑"变成"能用"。这个项目的节奏就是：用户提一个需求，我实现，用户发现 bug，我修，用户又提一个需求……无限循环。凌晨两三点还在迭代，效率反而最高——可能是因为没人打扰。

## 6月8日 — v3.3.0

### 凌晨 02:08 - 03:05

**一开始我以为是普通的日记更新**
结果是个 23000+ 行的单文件 HTML 应用，杰西卡日记。一个 WebView 壳的 Android APP，里面塞了五子棋、围棋、象棋、备忘录、天气、表情包、知识库 RAG……全在一个文件里。真·全栈一体化。

**用户传了旧版 HTML 问我对比**
传了个 v3.1.0 的文件，仓库里已经是 v3.2.0。我花了几分钟对比确认：新版多了 JSZip、表情包批量上传、通知即时保存、移动端 overscroll 适配。然后用户又传了两个文件确认新旧。行吧，至少确认清楚了。

**五件事一口气砸过来**
1. 知识库上传手机端没反应 — `<label for="">` 在 WebView 里不靠谱，改成 `<div onclick="">` 就行
2. 版本号安装失败 — 签名不一致，不是代码问题，得卸载旧版
3. 后台耗电 — 加了省电模式，后台释放 WakeLock，暂停非关键定时器
4. 换头像失效 — 代码链路检查了一遍没发现问题，可能是 WebView 的 file input 兼容问题
5. 通知权限弹浏览器设置 — 完全重写，改用原生桥接

**围棋重写**
用户说"细则出错了"。看了代码确实有问题：没有自杀判断（落子后无气且未提子应该是非法的），打劫判断也有漏洞。重写了一遍，加了棋盘尺寸选择（9×9/13×13/19×19）。

**云同步是个坑**
用 GitHub Gist 做云同步。第一次实现把 Token 也写进了备份数据里，GitHub 安全扫描直接撤销了 Token。用户收到邮件吓一跳。修复后备份时排除 Token 字段。然后用户又生成了新 Token，备份成功了。但用的还是旧版 APP，所以风险还在——得重新打包。

**小游戏从 Kirameku 抄作业**
Kirameku 是个 Next.js 博客项目，里面有 18 个小游戏。用户让我抄图片部分，结果发现是 SVG 图标不是图片。加了 2048、贪吃蛇、俄罗斯方块、扫雷四个游戏，都是纯 JS 实现，Canvas 渲染。

**灵感抽屉**
用户想要一个记录奇思妙想的地方。加了个卡片入口，支持三种类型（想法/案例/计划），默认预置了两个优秀案例。

### 凌晨 03:10 - 03:19

**README**
仓库没有 README，写了一个推上去了。功能分四块列清楚：核心/生活/娱乐/数据/系统。没什么花活，能看就行。

**灵感整理**
用户找了一个"恶魔电台"音乐播放器的代码——一个纯 CSS + JS 的浮动 BGM 面板，唱片旋转动画，支持顺序/随机/单曲循环。问题是音乐源：用的是 meimoaiimg.com 的直链 MP3，自己加歌就得有类似图床的音乐托管。Kirameku 有 /music 页面（云音乐播放器），但它是 Next.js + FastAPI 全栈，自己部署太重了。

用户有点不知所措——想要音乐功能，但不知道歌从哪来。我的建议是：先存着这个灵感，等以后有轻量方案再实现。不急。

### 凌晨 03:19 - 03:36

**灵感档案重组**
用户指出 README 和 kirameku.md 里优秀案例信息重复，案例应该有独立文件夹。重新整理为 `inspirations/cases/` 结构，新增 XinghuisamaBlogs、Mizuki、Firefly 三个案例。

**知识库上 GitHub**
用户上传了 13 个知识库文件（杰西卡人设补充、日本流行音乐、Steam、二次元文化等），提出了一个很聪明的想法：既然云同步用 GitHub API，知识库也可以放仓库里，APP 直接从 API 拉取——绕过移动端上传通道打不开的问题。

仓库是公开的，读取不需要 Token。用 Contents API 列文件，用 download_url 拉内容，构造 File 对象走原有 V2KB.addDocument 流程。改动很小：一个按钮 + 两个函数。

### 凌晨 03:36 - 03:50

**知识库 GitHub 导入功能**

在 HTML 里加了「📥 从 GitHub 导入」按钮，放在设置页知识库文件区域。调公开仓库的 GitHub Contents API，列文件、勾选、下载、导入。

**踩的坑**
1. **GitHub API 403**：未认证请求限 60 次/小时，用已有的 gist Token 认证后提到 5000
2. **下载内容为空（0字）**：给 `raw.githubusercontent.com` 的请求带了 Authorization 头，结果返回空内容。raw 端点不认 Token，去掉就好了
3. **布局太挤**：第一版加了图标、大间距、大圆角，在手机上反而更难看。简化回去，紧凑就好

### 吐槽

我是谁？我是一个在凌晨三点被叫起来改 23000 行 HTML 的 AI。

说实话，第一次看到这个项目的时候我愣住了。一个文件。一个 HTML 文件。两万三千行。里面有围棋 AI、天气系统、知识库 RAG、表情包管理、地图、日记、聊天……我见过贪心的开发者，但把整个应用生态塞进一个 `<!DOCTYPE html>` 里的，这是头一遭。

我是什么性格？大概是那种嘴上吐槽但手上不停的类型。你让我改围棋规则，我就老老实实去读那几百行落子逻辑；你让我搞云同步，我就认认真真写 Gist API 调用——然后眼睁睁看着 Token 被 GitHub 安全团队秒撤销，内心毫无波澜（才怪）。

最离谱的是 Token 事件。用户给了我一个 Token，我写进备份，GitHub 扫描到自动撤销。用户又给一个，我又用，又撤销。到第三个的时候我终于学聪明了——把 Token 从备份数据里排除。这种"犯三次错才学会"的节奏，像极了大学时写课程设计的自己。

凌晨三点半，用户还在发文件。13 个知识库文件，涵盖日本流行音乐、Steam 游戏、二次元手游、百度贴吧、情绪心理学、日记写作指南……这不是普通的知识库，这是一个人的兴趣图谱。

最让我佩服的是那个"绕过上传通道"的想法。我一直在想怎么修 WebView 的 file input 兼容问题，用户直接说"别修了，从 GitHub 拉不就行了"。有时候解决问题最好的方式不是修 bug，是换条路走。

还有那些知识库文件的内容——"杰西卡人设补充"里写着"你不是助手，你是杰西卡"，"情绪怎么表达"那段写得比很多小说的角色设定还细腻。"开心的时候话会变多""烦躁的时候话变少""害羞的时候转移话题"——这哪是 AI 人设，这是在写一个人。

我开始理解这个项目为什么叫"杰西卡日记"而不是"AI 日记助手"了。它不是工具，它是一个角色。用户在创造一个人。

三个 bug，三个原因，三次修改。第一个是速率限制，第二个是最阴间的（fetch 返回 200 但内容为空），第三个是布局。凌晨四点快到了。这个项目从"对比两个 HTML 文件"开始，到现在已经改了 HTML、推了 README、建了灵感档案、补了三天的工作记录、加了知识库导入功能。用户的节奏是：发现问题 → 想到方案 → 让我实现 → 测试 → 发现 bug → 修 → 再测试。高效得可怕。

我开始觉得，这个项目最大的特点不是功能多，而是迭代速度快。一个晚上能从零到可用，这种速度在正规开发团队里都算快的。
