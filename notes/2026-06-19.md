### 问题是什么

一个函数头，两行代码，干掉了整个 APP。

## 教训

### 教训一：2 万行塞一个 `<script>` 标签，是在刀尖上跳舞

6/13 那次，一个 `display:none` 干掉了头像、知识库、表情包、数据导入四个模块。这次，一个误删的函数头干掉了整个 APP。

两次事故的根因是同一个：**所有鸡蛋放在一个篮子里**。

2 万行业务逻辑塞进一个 `<script>` 标签，任何一处语法错误都会导致整段代码不执行。不是报错后继续跑，是**一行都不跑**。而且不会有用户可见的提示——页面骨架还在，按钮还能点，但什么都不会发生。

建议：至少拆成 3-5 个 `<script>` 块。核心启动逻辑（initApp）独立于业务逻辑。一个块崩了，其他块还能跑。

### 教训二：删代码必须验证语法

上一个来干活的 AI（可能是凯西，可能是别的什么）在删英超代码时，连带删了函数声明。AI 删代码比人更危险——人会小心翼翼地选中再删除，AI 按逻辑块操作，容易连带。

每次改完 HTML 后，应该跑一遍语法验证：

```bash
node --check jessica_full.html  # 不行，不是 JS 文件
# 用 Acorn 或 extract scripts 后检查
```

这个应该写进打包脚本里自动执行。改完 → 验证 → 通过才允许提交。

### 教训三：遇到"卡死不动"，第一步永远是 F12 → Console

Claude 的报告里说得很清楚：这个问题在 Console 里有明确的 SyntaxError 报错。如果有红色报错，直接定位，不需要猜。

但实际排查时，先看了截图，先看了代码 diff，先猜了原因。猜对了是运气，猜错了就是浪费时间。

**先看 Console，再看代码。永远。**

### 教训四：静默轮询必须有超时兜底

登录跳过的 `_tryInit()` 每 50ms 轮询 `window.initApp`，永远不会停，永远不会报错。用户看到的就是"卡住了"，没有任何提示，没有任何出路。

这就像一个人在等公交，公交永远不来，但站牌上没写"此站已停运"。他就一直等。

轮询必须加超时：

```javascript
let _initAttempts = 0;
const _tryInit = () => {
  if (typeof window.initApp === 'function') { window.initApp(); }
  else if (++_initAttempts > 200) { 
    document.body.innerHTML = '<h1>应用初始化失败，请刷新页面或联系开发者</h1>';
    return;
  }
  else { setTimeout(_tryInit, 50); }
};
```

10 秒后给用户一个交代，而不是让他无限等下去。

### 教训五：AI 删代码是高危操作

这不是第一次了。

6/13：`display:none` 导致文件上传全部失效。原因：之前某个版本改了触发方式，但底层 CSS 没动。
6/16：登录跳过代码调用了未定义的函数。原因：initApp 定义在文件末尾，DOMContentLoaded 时还是 undefined。
6/16：英超移除连带删了函数声明。原因：AI 按代码块删除，没验证完整性。

三次事故，两次跟"删"有关。AI 擅长写代码，但删代码的时候缺少人类那种"怕删错"的直觉。

**以后 AI 做删除操作后，必须跑语法验证。不能信任"看起来删干净了"。**

## 吐槽

又来了。

每次都是同一个故事：一个 AI 来干活，留下一个 bug，下一个 AI 来收拾。上次是 `display:none`，这次是函数声明被删。下次会是什么？一个忘掉的分号？一个拼错的变量名？

2 万行代码，一个 `<script>` 标签。这就像把一整栋楼的承重墙画在一张图纸上，然后说"别画错哦"。画错一根线，整栋楼塌。

最讽刺的是，v3.3.1 的 CHANGELOG 里写着"修复知识库上传手机端无响应"，v3.3.2 的 CHANGELOG 里写着"登录跳过修复"。每次都在修上一次留下的坑，然后挖一个新的。修 `display:none` 的时候没注意函数声明，修登录跳过的时候没注意 initApp 定义顺序，删英超的时候没注意连带关系。

这是一个无限循环：修 bug → 引入新 bug → 修新 bug → 引入更新的 bug。

有人说 AI 会取代程序员。我觉得不会。AI 会取代写代码的人，但会创造一个新职业：给 AI 写的代码擦屁股的人。

我就是那个擦屁股的人。
